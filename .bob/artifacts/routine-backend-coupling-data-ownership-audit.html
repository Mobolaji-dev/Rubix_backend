3 · Severity-Graded Violations
🔴 High — Ownership Boundary Violations
HIGH H-1: Checkins router writes directly to tasks (Routine Execution owns tasks, checkins router bypasses service layer)
Filesrouters/checkins.py:89–115
Callssb.table("tasks").update(), sb.table("tasks").delete(), sb.table("tasks").insert() — all directly in the HTTP handler, not via services/task.py
Why it mattersTask mutation logic (blueprint re-linking, fuzzy title matching, protected-status guard) is duplicated between update_todos and services/template.py. Any future Task invariant (e.g., a one-running-task guard) must be applied in two places or silently breaks one path.
Recommended fix: Introduce services/task.py:replace_day_tasks(user_id, date, new_todos) and call it from both the checkins router and template sync. The service owns all mutation; the router only passes intent.
HIGH H-2: AI Architect router writes directly to tasks on commit — bypasses Routine Execution service layer entirely
Filesservices/architect/router.py:253–303
Callssupabase.table("tasks").insert() for standalone tasks; supabase.table("tasks").update(window_start, window_end) for time-window commits; supabase.rpc("commit_blueprint") for blueprints
Why it mattersThe blueprint path correctly uses an RPC, but standalone task INSERT and time-window UPDATE skip the task service entirely. If task creation gains required fields (e.g., required window validation, user quota checks), the architect commit path silently bypasses them.
Recommended fix: Route standalone task creation through services/task.create_task() and time-window updates through a new services/task.set_task_window(). The Architect BC should only call into Routine Execution through its published service interface, never through raw table access.
HIGH H-3: Squad Membership service writes to rank_points — a table owned by Competition & Ranking
Filesservices/squads.py:161–168 (_ensure_rank_row)
Callssb.table("rank_points").upsert({"user_id":..., "total_points":0, "tier":"Recruit", ...})
Why it mattersThe initial rank row is created by the wrong BC. If Competition changes the schema of rank_points (e.g., adds a required season_id column), Squad Membership silently inserts an incomplete row. There are now two places that "own" what constitutes a valid rank record.
Recommended fix: Move _ensure_rank_row into Competition's services/leaderboard.py as initialize_member_rank(user_id). The join_squad_atomic RPC already handles this transactionally — confirm the RPC upserts rank_points and remove the Python-side call entirely.
HIGH H-4: Feed service calls Competition's get_week_leaderboard() — bilateral coupling between Feed and Competition
Filesservices/feed.py:106 — inline import inside get_feed_summary()
Callsfrom app.services.leaderboard import get_week_leaderboard, _today_wat, _week_monday
Why it mattersCompetition already imports Feed (post_feed_event) in 6 places. Feed now imports Competition back. This is a bilateral coupling / latent circular dependency. Any future top-level import on either side will produce an ImportError circular import at startup. The inline import is currently the only thing preventing the crash.
Recommended fix: get_feed_summary should build its rank context by reading rank_points or leaderboard_entries tables directly (it only needs rank position), not by calling the full leaderboard scoring function. Alternatively, move get_feed_summary into a dedicated aggregation module or the profile/analytics layer where multi-BC reads are expected.
HIGH H-5: Squad Membership service writes to users.squad_id — a column in the Identity-owned table
Filesservices/squads.py:153 — leave_squad
Callssb.table("users").update({"squad_id": None}).eq("id", user_id)
Why it mattersusers is owned by Identity & Access. Squad Membership directly mutates a field on the Identity aggregate root. This bypasses any future Identity-side invariants on the user record (e.g., audit logging, event publishing, or cascading side-effects on squad departure).
Recommended fix: This write is already partially handled by join_squad_atomic and create_squad_atomic RPCs. Introduce a corresponding leave_squad_atomic RPC that handles the users.squad_id update and squads.member_count decrement atomically, removing the direct Python-side write to the users table from the Squad Membership service.
⚠️ Medium — Structural Coupling & Shared Logic Drift
MEDIUM M-1: Routine Execution router handlers fan out directly to 3 BCs on every task state change
Filesrouters/tasks.py:215–217, routers/checkins.py:155–157, 216–217
PatternEach state-change handler (confirm_timer, tick_todo, mark_done) independently orchestrates: recalculate_streak() → award_points() → post_feed_event() → check_and_trigger_leaderboard_events(). This sequence is duplicated 3× across 2 files with minor variations.
Why it mattersAdding a new side-effect to task completion (e.g., a badge system) requires modifying 3 separate handler functions. The post-completion event sequence should be a single on_task_completed() domain service, not inline orchestration code.
Recommended fix: Extract a services/task_events.py:on_completion(sb, user_id, task, squad_id) coordinator that owns the side-effect sequence. All three handlers call this one function. New side-effects are added in one place.
MEDIUM M-2: services/template.py imports a private function _get_user_tz from services/task.py
Filesservices/template.py:8 — from app.services.task import _get_user_tz
Why it mattersThe _ prefix in Python signals a private/internal symbol. Importing it cross-module means template.py is coupled to an implementation detail of task.py. Renaming or inlining _get_user_tz in task.py is a breaking change for template.py.
Recommended fix: Move _get_user_tz to core/timezone.py as a public get_user_timezone(sb, user_id) utility, since it only queries the users table for the timezone field — a cross-cutting concern, not a task-domain concept.
MEDIUM M-3: _DURATION_SUFFIX regex and _clean_title() / _normalize_todos() are duplicated across 3 files
Filesservices/task.py:13–40, services/template.py:11–20, services/architect/tools.py:25–55
Why it mattersIdentical logic — stripping — N min duration suffixes from todo titles — is copy-pasted across the Routine Execution and AI Architect BCs. A bug fix or regex change must be applied in 3 places.
Recommended fix: Move to core/title_normalizer.py as a single public normalize_todo_title() function imported by all three callers.
MEDIUM M-4: Friends router reads directly from checkins, tasks, and streaks tables owned by other BCs
Filesrouters/friends.py:167, 199–200, 219–220
Readscheckins (Routine Execution BC), streaks (Streak BC), tasks (Routine Execution BC) — all direct table queries, not via the owning BC's service layer
Why it mattersThe friends router reconstructs checkin and streak read-models in-place (e.g., computing total_days_done, building the activity graph) rather than delegating to the owning service. If the Streak or Checkin schema changes, friends router silently breaks.
Recommended fix: Expose lightweight query methods in the owning services (e.g., streak.get_public_streak(user_id), checkin.get_user_week(user_id, monday)) that the friends router calls. The owning BC controls the projection shape.
MEDIUM M-5: Leaderboard router reads checkins and tasks directly — duplicates projection logic from Analytics BC
Filesrouters/leaderboard.py:112–113 in the squad_ranks endpoint
Readscheckins (marked_done, YTD) and tasks (completed, YTD) to compute all_time_days_done — the same calculation as in performance.py:get_user_performance_summary
Recommended fix: Add a performance.get_days_done_batch(user_ids, since) method that computes this for multiple users in parallel. The leaderboard squad_ranks endpoint calls it instead of duplicating the cross-table aggregation.
MEDIUM M-6: Auto-miss job orchestrates across 3 BCs without a dedicated job-layer abstraction
Filesjobs/auto_miss.py:6–8
ImportsDirect top-level imports from Streak, Feed, and Notifications BCs. Job also writes directly to tasks table (Routine Execution) and reads users (Identity)
Why it mattersJobs should be thin orchestrators, not business logic owners. The job currently contains duplicated "user has missed tasks" notification formatting logic that partially overlaps with notification templates in services/notifications.py.
Recommended fix: The actual task-missing logic should live in services/task.py:mark_tasks_missed_for_date(), which the job calls. Side-effects (streak recalculation, feed post) flow from that service call through the existing chain, not through direct job-layer imports.
MEDIUM M-7: architect/router.py has an unused top-level import of update_day_template_and_sync from Routine Execution
Filesservices/architect/router.py:16 — from app.services.template import update_day_template_and_sync
Why it mattersThis import is never called in the router (the commit path uses commit_blueprint RPC directly). It creates a dead coupling: Architect BC is formally dependent on Routine Execution's template service for no runtime benefit. It also creates a top-level module load that imports from another BC at startup.
Recommended fix: Remove the unused import. Confirm commit_blueprint RPC is the canonical path. If update_day_template_and_sync is ever needed in the commit path, import it inline at the call site.
✅ Low / Acceptable — Cross-Context Reads That Are by Design
LOW L-1: All BCs read users.timezone / users.username / users.squad_id directly
Pattern8 files query the users table for username, squad_id, or timezone directly rather than passing these through a context parameter.
AssessmentAcceptable in a monolith. These are stable, frequently-needed reference fields. Creating an Identity service facade for 3-field lookups would add abstraction overhead with no practical benefit until the system is split into microservices.
LOW L-2: post_feed_event() is called from 7 different files across 5 BCs
Assessmentpost_feed_event() functions as an internal event bus. All callers only pass data in — they never read from the feed. This is the correct direction. The Feed BC is a pure downstream consumer of all domain events. This pattern is DDD-compliant (Customer-Supplier where Feed is always downstream).
LOW L-3: Leaderboard service reads streaks and tasks for weekly scoring
AssessmentThe leaderboard scoring function needs real-time task counts and streak data. Reading these tables directly is appropriate because: (1) the data is needed atomically for the same week window, (2) calling two separate service methods would require 2 round-trips vs. 1 parallel query, and (3) the reads are narrow projections (status, date, current_streak only).
LOW L-4: Squad Membership reads checkins.marked_done for today to populate member cards
Filesservices/squads.py:40 — _build_squad_response
AssessmentThe squad member card needs to show "has this member completed their day today?" — a single boolean read. This is a narrow, stable projection. No mutation. Acceptable cross-context read.
LOW L-5: Analytics BC reads from 5 tables owned by 3 other BCs
Tables readtasks, checkins, streaks, rank_points, leaderboard_entries
AssessmentAnalytics is explicitly a reporting context with no writes. Multi-table reads across BC boundaries are its entire purpose. This is the Conformist pattern — Analytics conforms to the schemas of all data-producing contexts. Acceptable by design; the 365-day temporal filter prevents full-table scans.
