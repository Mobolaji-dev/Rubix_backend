Identity & Access
Who the user is, how they authenticate, and whether they are allowed in
Core Domain
Owned Modules
Routers
  • routers/auth.py
Core / Infrastructure
  • core/auth.py
  • core/config.py
  • core/supabase.py
  • core/timezone.py
  • core/limiter.py
  • core/logging.py
Services
  • services/email.py (auth emails only)
Schemas
  • schemas/schemas.py (RegisterRequest, LoginRequest, TokenResponse, UserResponse)
Database Tables
  • auth.users (Supabase managed)
  • users (public profile row)
  • password_reset_tokens
Migration
  • migrations/03_handle_new_auth_user.sql
Primary Responsibility
Owns the full lifecycle of a User identity: registration, login (delegated to Supabase GoTrue), token validation (ES256 JWT / JWKS local verification), password reset flow, profile updates (username, email, phone, timezone), and the CurrentUser / CurrentUserWithEmail FastAPI dependency that every other context consumes as its primary authentication gate.

Aggregates & Value Objects
User (aggregate root) JWT Token PasswordResetToken Timezone

Ubiquitous Language
  • User — a registered identity with a public username
  • Onboarded — user has set username + phone (no user_ prefix)
  • CurrentUserWithEmail — gated access requiring a verified email
  • Reset Token — single-use SHA-256 hashed token

Upstream / Downstream Dependencies
Provides to all BCs: CurrentUser identity user_id string
External: Supabase Auth (GoTrue) Resend (email)

Rationale: auth and identity warrant their own BC because they cross-cut all other contexts — every FastAPI route is downstream. Supabase GoTrue is an external conformist system; the local public.users table is owned here and acts as the canonical identity record inside the monolith.

Routine Execution
Planning, executing, and completing daily tasks against a repeating blueprint
Core Domain
Owned Modules
Routers
  • routers/tasks.py
  • routers/checkins.py
  • routers/templates.py
  • routers/dashboard.py
Services
  • services/task.py
  • services/checkin.py
  • services/template.py
Schemas
  • schemas/task.py
  • schemas/schemas.py (CheckinResponse, TodosUpdate, WeekCheckinResponse, TemplateUpdate, TemplateResponse)
Database Tables
  • tasks (aggregate, all ops)
  • checkins (daily sealing record)
  • day_templates (weekly blueprint)
Background Jobs
  • jobs/auto_miss.py (run_auto_miss, run_end_of_day_warning)
Primary Responsibility
Owns the complete lifecycle of a Task — from blueprint seeding through timer start/extend/confirm/abandon to auto-miss. Manages the Checkin record (daily progress snapshot and the 80% sealing gate). Owns DayTemplate (the repeating blueprint that seeds each weekday's tasks). The dashboard summary endpoint is a read-model aggregated from this BC's tables.

Aggregates & Value Objects
Task (aggregate root) Checkin DayTemplate TaskStatus TimerWindow AllocationMinutes

Ubiquitous Language
  • Blueprint — the repeating per-day task plan (stored in day_templates)
  • Seeding — materialising today's tasks from the blueprint at first access
  • Running — a task with an active countdown timer
  • Mark Done — sealing a day after ≥80% completion
  • Reignite — resetting a missed/completed task back to unallocated
  • Auto-Miss — system-driven miss when a task's date has expired

Downstream Consumers
Streak Context Competition Context Squad Feed Context AI Architect Context Analytics Context

Rationale: Tasks, Checkins, and DayTemplates form a tightly coupled cluster around a single domain concept — "did the user execute their routine today?" They share tables, seeding logic, and a common aggregate root (Task). Separating templates from tasks would require constant cross-BC queries just to serve a checkin response.

Streak & Consistency
Tracking the user's consecutive-day execution record and broadcasting milestones
Supporting Domain
Owned Modules
Routers
  • routers/streak.py
Services
  • services/streak.py
Schemas
  • schemas/schemas.py (StreakResponse)
Database Tables
  • streaks (current, longest, last_done_date)
External PL/pgSQL RPC
  • recalculate_streak_db (atomically reads checkins + tasks, writes streaks)
Primary Responsibility
Owns the Streak aggregate: computing and persisting current and longest consecutive-day counts. Detects streak breaks and milestones (every 10 days) and emits domain events as side-effects (push notifications + squad feed posts). The RPC strategy consolidates all reads and writes into a single PL/pgSQL transaction to prevent concurrent race conditions.

Aggregates & Value Objects
Streak (aggregate root) ConsecutiveDays LastDoneDate

Ubiquitous Language
  • Streak — the count of consecutive days with at least one completion
  • Streak Break — current_streak drops to 0
  • Milestone — streak reaches a multiple of 10
  • Last Done Date — the most recent date the user completed something

Integration
Consumes events from: Routine Execution
Emits events to: Squad Feed Context Push Notification Infra

Rationale: Streak is conceptually distinct from task execution — it is a longitudinal measurement, not an action. It is also consumed independently by the Friends, Squad, and Leaderboard contexts. It has its own table, its own RPC, and its own event types. A separate BC boundary prevents the streak calculation from becoming entangled with task-state mutation logic.

Competition & Ranking
Weekly squad leaderboards, rank tiers, promotions, demotions, and all-time points
Core Domain
Owned Modules
Routers
  • routers/leaderboard.py
Services
  • services/leaderboard.py
  • services/rank_system.py
Schemas
  • schemas/leaderboard.py
Background Jobs
  • jobs/weekly_reset.py
Database Tables
  • rank_points (total_points, tier, division, shield_count)
  • leaderboard_entries (weekly historical snapshots)
External PL/pgSQL RPCs
  • award_points_atomic
  • acquire_job_lock / release_job_lock
Primary Responsibility
Owns the RankPoints and LeaderboardEntry aggregates. Manages the weekly scoring algorithm (completion % + streak as tiebreaker), atomic point awarding, tier transitions (Recruit → Consistent → Disciplined → Committed → Elite → CMPDx), division promotions/demotions on weekly close, and the distributed WeeklyReset job (10 squads in parallel behind a semaphore with job locking).

Aggregates & Value Objects
RankPoints (aggregate root) LeaderboardEntry Tier Division WeeklyScore RankPosition

Ubiquitous Language
  • Tier — named rank bracket (Recruit … CMPDx)
  • Division — sub-rank within a tier (3 = bottom, 1 = top)
  • Promotion — moving up a division or tier after a top-2 weekly finish
  • Demotion — dropping a division/tier after finishing last in squad ≥ 3
  • Week Close — the Monday job that seals weekly results and triggers rank changes
  • Rank Surpassed — real-time overtake of another squad member mid-week

Integration
Triggered by: Routine Execution (task confirm)
Emits to: Squad Feed Context Push Notification Infra

Rationale: The leaderboard system has its own complex scoring formula, tier ladder, job scheduling, and historical snapshot table. It is not just a view over tasks — it applies game-design rules that evolve independently. rank_system.py and leaderboard.py together form a rich domain model that belongs in its own context.

Squad Membership
Creating, joining, leaving, and managing the accountability groups users compete inside
Supporting Domain
Owned Modules
Routers
  • routers/squads.py
  • routers/friends.py
  • routers/contact.py
Services
  • services/squads.py
  • services/email.py (send_squad_invite)
Schemas
  • schemas/squads.py
  • schemas/schemas.py (FriendRequestResponse, FriendResponse, FriendWeekResponse, FriendStreakResponse, FriendGraphResponse)
Database Tables
  • squads
  • friendships
  • friend_requests
External PL/pgSQL RPCs
  • create_squad_atomic
  • join_squad_atomic
  • accept_friend_request_atomic
Primary Responsibility
Owns the Squad and Friendship aggregates. Manages squad creation (unique invite code generation), invite-code joining, contact-number search (phone normalisation for Nigerian numbers), friend request lifecycle, and email-based squad invites. Exposes friend-visibility read models (week view, streak, activity graph) gated by friendship status.

Aggregates & Value Objects
Squad (aggregate root) Friendship FriendRequest InviteCode MemberCount NigerianPhoneNumber

Ubiquitous Language
  • Squad — an accountability group of up to 6 users
  • Invite Code — a 6-character uppercase alphanumeric join token
  • Friend Visibility — ability to see another user's week/streak/graph
  • Contact Search — matching phone numbers against registered users

Integration
Provides to: Competition Context (squad_id anchor) Squad Feed Context (squad_id anchor)
External: Resend (squad invite email)

Rationale: Squad and Friend are social structures that exist independently of any particular week's performance. They define who can see what and who competes together. Friends are grouped here rather than having their own BC because friend-visibility (week view, streak peek) directly reads from the Squad Membership tables and is gated by friendship status — they share the same access-control invariant.

Squad Activity Feed
Recording and broadcasting everything that happens inside a squad as a real-time activity stream
Supporting Domain
Owned Modules
Routers
  • routers/feed.py
Services
  • services/feed.py
  • services/notifications.py
Schemas
  • schemas/feed.py
Database Tables
  • feed_entries (event log)
  • feed_views (seen-by tracking)
  • push_subscriptions (Web Push registrations)
Primary Responsibility
Owns the FeedEntry aggregate — the append-only squad event log. Provides the post_feed_event() domain service called by every other context to broadcast squad-visible events. Manages cursor-based pagination of feed entries and "seen-by" tracking. Owns the PushSubscription aggregate (VAPID Web Push device registrations) and dispatches Web Push notifications to squad members and individual users as fire-and-forget side-effects.

Aggregates & Value Objects
FeedEntry (aggregate root) PushSubscription FeedEventType FeedCursor post_feed_event() (domain service)

Ubiquitous Language
  • Feed Event — a squad-scoped broadcast record of something that happened
  • Event Types — task_completed · day_done · day_missed · joined_squad · streak_broken · streak_milestone · rank_changed · rank_surpassed · leaderboard_topped · rank_dropped · timer_abandoned
  • Seen By — the list of squad members who have viewed an entry
  • Push Subscription — a device-level Web Push endpoint registration

Integration — Inbound Events
Routine Execution Streak Context Competition Context Squad Membership

Rationale: The feed is a pure event-store and notification dispatcher. It holds no business rules of its own — its invariant is append-only. All other contexts publish into it but none own it. Combining push notifications here is justified because both feed and push share the same trigger (a domain event occurs) and the same audience (squad members or the acting user).

Analytics & Performance Insights
Computing and caching derived metrics about a user's long-term execution patterns
Generic Subdomain
Owned Modules
Routers
  • routers/profile.py
Services
  • services/performance.py
Schemas
  • schemas/performance.py
Read Sources (no owned writes)
  • tasks (read-only, 365-day window)
  • checkins (read-only, 365-day window)
  • streaks (read-only)
  • rank_points (read-only)
  • leaderboard_entries (read-only)
Primary Responsibility
A pure read model / reporting context. Computes derived metrics from raw task and checkin data: all-time and 30-day completion rates, peak/dead days (weighted by volume), 4-week trends, average tasks per day, 14-day streak history booleans, and week-by-week history with leaderboard snapshots. Maintains an in-memory cache (30-second TTL for performance stats, 5-minute TTL for week history). Exposes a public (unauthenticated) profile endpoint. Never writes to any table.

Value Objects & Services
PerformanceSummary AISignals WeekSummary DaySummary get_user_performance_summary() get_ai_signals() calculate_week_history()

Ubiquitous Language
  • AI Signals — structured performance data fed to the Architect agent
  • Peak Day — day-of-week with highest weighted completion score
  • Dead Day — day-of-week with lowest weighted completion score
  • Days Survived — all-time unique dates with at least one completion

Consumers
AI Architect Context (AISignals) Public profile endpoint

Rationale: This context owns zero writes. It is a reporting / analytics projection over data owned by other BCs. Separating it prevents performance calculation logic from polluting the transactional contexts and allows caching strategies (in-memory, future Redis) to be managed independently without touching business rules.

AI Architect
A conversational LLM agent that understands the user's patterns and proposes structured routine changes
Core Domain
Owned Modules
Routers
  • routers/architect.py
Services (entire architect/ package)
  • services/architect/router.py
  • services/architect/graph.py
  • services/architect/nodes.py
  • services/architect/state.py
  • services/architect/tools.py
  • services/architect/llm.py
  • services/architect/prompts/systemprompt.py
  • services/architect/validate_regex.py
Schemas
  • schemas/architect.py
Database Tables (owned)
  • architect_sessions (conversation history + pending_proposal)
  • user_context (durable user context: day_shape, habits, etc.)
External Infrastructure
  • OpenRouter (LLM API gateway)
  • LangGraph (agent loop: agent → tools → agent)
Primary Responsibility
Owns the ArchitectSession and UserContext aggregates. Runs a ReAct-style LangGraph agent loop that reasons over the user's performance signals and blueprint, then stages structured proposals (blueprint change, standalone task, or time window) for explicit user confirmation before writing anything to the Routine Execution context. Acts as an Anti-Corruption Layer translating between the LLM's free-text reasoning and the strict domain schemas of the Routine Execution context.

Aggregates & Value Objects
ArchitectSession (aggregate root) UserContext Proposal (blueprint | standalone_task | time_window) AgentState architect_graph (LangGraph)

Ubiquitous Language
  • Session — a persistent conversation thread between user and the agent
  • Proposal — a staged, uncommitted plan change awaiting user confirmation
  • Commit / Reject — user explicitly accepts or discards a staged proposal
  • User Context — durable profile of how the user operates (day_shape, derail_pattern, etc.)
  • AI Signals — performance metrics consumed from the Analytics BC

Integration
Reads from: Analytics BC (AISignals, week history) Routine Execution (tasks, day_templates)
Writes to (on commit only): Routine Execution (via commit_blueprint RPC or tasks INSERT)
External: OpenRouter (LLM) LangGraph (agent loop)

Rationale: The AI agent is architecturally distinct because it introduces a non-deterministic, conversational loop not found anywhere else. It owns its own session state and user-context store, has a completely different execution model (LangGraph), and deliberately decouples LLM reasoning from transactional writes via the proposal/commit pattern. It is a Core Domain differentiator — no generic off-the-shelf solution produces a performance-aware routine coach.
